# Phase 3 入场券：启动技能（节律记忆第一个用户）

> 状态：设计草案，待用户过目后实施。
> 依据：方案 v0.1 §11 Phase 3 / §4.5 节律记忆族 / §6.2 护栏；
> 场景目录 #13（开机启动组合）、#14（解锁恢复，**用户已定：举牌确认制，
> 不自动启动**）；修订登记 §5（交互总原则）。
> 信号盘点基于 2026-10-24~28 真实语料（约 9600 条事件）。

## 1. 一句话定义与范围收窄

**启动技能 v1 = 「解锁后的开工组合助手」**：观察每次解锁后一段时间内你
实际开启的程序集合，学成"开工组合"（按工作日/周末分桶），在下次解锁后
**以建议档起步**帮你拉起组合——先当跟班的，不抢方向盘。

范围收窄（本节即"明确不做"清单）：

| 不做 | 归属 |
|---|---|
| 到点预告（"你通常 18:20 收尾"） | 场景 #20，纯提醒，独立小场景，后做 |
| 离开模式（锁屏静音+通知折叠） | 场景 #15，关联记忆，Phase 4 |
| 网络/位置上下文（公司 WiFi→工作组合） | 关联记忆，Phase 4 |
| 日历忙闲任何形式 | 红线（修订 §6：只外推行为节律，不断言日历事实） |
| 开机自启管理（改注册表/启动文件夹） | 元红线：永不修改自身持久化配置与自启项 |

方案原验收标准照搬为本技能验收：**一周后自动启动清单与真实习惯重合**
（§8 给出可计算定义）。

## 2. 五问过关

| 问 | 回答 | 证据/依据 |
|---|---|---|
| 信号是结构化事件吗？ | ✓ session_unlock / power resume / foreground changed（仅 exe 名，纯标识） | 已在 event_raw 流动 4 天 |
| 动作是可逆旋钮吗？ | △ 拉起进程在动作白名单内（方案 §6.2），但 undo **有损**（关掉自己拉起的实例 ≠ 无损还原）→ 缓解：v1 只出建议（无损）；执行档严格 explicit 确认后才开 | 方案 undo 分级原文："启动应用=关掉自己拉起的实例（有损），下次不再启动优先" |
| 有客观纠正信号吗？ | △ 弱于音量：音量有精确纠正值，启动只有接受/拒绝二值。可用信号：建议被点掉、组合成员被手动开启（missed_need）、拉起后被秒关且从未前台 | §6 归因表 |
| 偏好重复吗？ | ✓ 每个工作日解锁即一次重复；真实语料：工作日开工 07:36/07:39 高度稳定 | §3 信号盘点 |
| 有时间窗口吗？ | ✓ 双重窗口：观察窗（解锁后 N 分钟内的启动集合）+ 节律分桶（工作日/周末 × 深夜过滤） | §3 |

结论：五问 3✓ 2△，两个 △ 均有护栏缓解，且风险档"零~低"从建议档起步
成立。**过。**

## 3. 信号盘点（真实语料，2026-10-24~28）

| 信号 | 库内条数 | 评估 |
|---|---|---|
| `system.session/session_unlock` | 8 次 | **贵而稳**：每天 1~2 次；工作日开工 07:36、07:39 两日完全一致；周末（周日）09:54；10-26 17:02 为异常日样本 |
| `app.foreground/changed` | 2460 | **充足**：解锁后 10 分钟窗口 top：explorer(46)、ZCode(10)、SLBrowser(8)、GameViewer(6)、msedge(3)——组合原料真实存在且可提取 |
| `system.idle/*` | 0 | 今晚刚上线，暂无语料；**v1 不依赖它**（它是收尾节律/#20 的原料），数据自然积累 |
| `system.power/resume` | 3 | 开机场景原料，v1 与 unlock 合并处理（取开机后首次解锁） |

设计结论：
- **v1 的"节律"体现在记忆内容（分桶+过滤），不在触发器**——触发事件
  就是已有的 session_unlock，零新传感器、零 cron。真正的纯时间触发
  （无会话事件的到点预告）留给场景 #20；
- 解锁样本每天 1~2 个 → **学习慢是本性**：最少样本门槛 N=5 才允许生成
  草稿组合（config），宁可不学不可学错；
- exe 身份直接用前台流里的 exe 名（纯标识，红线安全）。

## 4. 记忆表示：零 DDL 变更（复用 A1 五表）

> **修订 §19 反驳修订版（2026-10-28）**：观察层只采集；定量统计
> （StatsDraftAnalyzer）是 **v1 正式机制**（节律归纳属查表问题领地），
> 职责是生产"够格被用户纠正的草稿"；研究层 agent 的领地是泛化与
> 开放世界推断。已登记缺口（壳进程污染 / 置信公式校准）见 §19.3。

节律不新增表——它就是一条**条件型偏好**：

```
preference:
  pref_key  = "startup.launch_set"
  scope     = "class"
  scope_key = "schedule:weekday" | "schedule:weekend"    # v1 二分桶
  value     = {"apps": [{"exe": "ZCode.exe", "rate": 0.9},
                         {"exe": "msedge.exe", "rate": 0.6}]}
  # rate = 最近 N 次解锁窗口内该 exe 的出现率（滚动）；成员级淘汰线进 config
  source    = "observed"（草稿）→ "explicit"（用户确认组合后）
  state     = draft → active
evidence:
  kind = "event"，ref_id = 该次 session_unlock 的 event_raw.id
  detail = {"window_exes": [...], "dow": 2, "hhmm": "0736"}
  # 每次解锁一条证据——组合成员的 rate 可从证据链重算（可溯源、可回放）
```

- 作用域链照常：exception（"周日别管我"）> schedule:weekend/weekday >
  global；
- **衰减淘汰**（方案 §4.3：启动场景自动淘汰失效项）= rate 滚动下降到
  淘汰线以下即从 value 中移除，无需新机制；
- 台账/undo/置信度分级全部复用现有技能层机制。

## 5. 触发、观察与"何时开口"

```
session_unlock ──┬─> RhythmObserver（观察层，永远在跑）
                 │     解锁后观察窗 15min（config）内收集窗口 exe 集合
                 │     → 滚动更新 draft 组合 + evidence
                 │
                 └─> StartupSkill（触发层，conf 分级后才有动作）
                       unlock + 非深夜(0-6点) + 组合 draft/active
                       → 等 90 秒（config）：等你自己开首波程序
                          ├─ 窗口内已手动开 ≥60% 组合成员 → 不弹，
                          │   记 missed_need（静默学习，计算礼貌）
                          └─ 否则 → 建议 toast：「开工组合：A、B、C，
                              要我下次自动拉起吗？」[启动] [不用] [仅这次]
```

要点：
- **90 秒延迟**：你自己正在开程序时弹建议是打扰；等你开完首波还缺一大半
  才值得开口；
- **手动开 ≥60% 则彻底沉默**：missed_need 是最好的学习原料，比弹窗珍贵；
- 建议档动作本身无损（弹一条 toast），执行档动作才碰进程。

## 6. 归因决策表（A5 草案，规则编号 S*）

| 规则 | 场景（建议档） | reaction / quadrant | 学习动作 |
|---|---|---|---|
| S1 | 点了[启动]/[仅这次] | accept / correct_detection | 组合成员 rate 棘轮升 |
| S2 | 点了[不用] | correct / false_alarm | 组合 confidence ×γ(0.8)；连点两次不用 → 降回纯观察 + 面板标红 |
| S3 | 60s 无响应（忽略） | ignore / non_response | 不罚；连续 3 次忽略 → 沉默一周（观察期冷却） |
| S4 | 窗口内手动开了组合成员 | missed_need / missed_need | **升档燃料**：missed 计数进组合，累计 3 次 + draft 面板确认 → 允许进执行档 |
| S5 | 窗口内开了组合外的新程序 | （无动作） | 新成员候选：出现率过线自动进 draft 组合 |
| SN1 | 深夜/异常时段解锁 | 不触发 | ——（时段过滤在触发层完成） |
| SN2 | 样本 < N(5) | 不触发 | 纯观察积累 |

执行档（explicit 确认 + conf≥0.85 后才可能到达）追加：
| 规则 | 场景 | 处置 |
|---|---|---|
| S6 | 拉起后 5 分钟内被关且从未前台 | correct / false_alarm，confidence ×γ_hard(0.5)，undo 自动执行（关掉本次拉起实例） |
| S7 | 面板撤销 | reject / false_alarm；"下次不再启动"（exception 写入）优先于逐个关闭 |

## 7. 执行器与护栏（executors/launch.py）

1. **学习型白名单**：只允许拉起 **evidence 里出现过的 exe**（从历史前台
   流解析出的绝对路径）——不是任意路径执行器；解析失败的成员跳过并留痕；
2. **防重复拉起**（方案原文）：执行前枚举正在运行进程 + 只读扫描已有自启
   项（注册表 Run 键 + 启动文件夹），已在跑/已自启的成员跳过；
3. **延迟预算**：建议档秒级即可（无防爆需求）；执行档拉起用 detached
   Popen，不等待；
4. undo 分级照方案：关掉本次拉起的实例（有损）+"下次不再启动"优先；
5. 台账不可豁免：建议也是动作（exec_mode=suggest 落账，四象限不缺角）；
6. 全局暂停/日预算/同组合冷却照常适用。

## 8. 爬升顺序与验收

1. **第 1~2 周纯观察**：RhythmObserver 跑着，draft 组合在面板待确认区
   生长，零通知零动作；
2. **观察达标后开建议档**（draft 样本 ≥N 且用户在面板确认过组合一次）；
3. **执行档**：S4 累计 missed_need ≥3 且用户 explicit 确认"可以自动拉起"；
4. **验收**（方案原文可计算化）：**重合率 = 建议组合与观察窗实际开启集合
   的 Jaccard，连续 7 天 ≥0.6** 即"自动启动清单与真实习惯重合"。

## 9. 与方案 v0.1 的偏差预登记

1. v1 不做"组合拉起"的自动执行起步——从建议档爬升（方案 Phase 3 未明确
   起步档位，按信任分级原则取建议起步；场景 #14 的"举牌确认制"精神
   推广到 #13）；
2. 节律记忆零新表（方案未规定存储形态；复用 preference+evidence 比加表
   更符合"事实与信念分离"的最小充分原则）；
3. 触发器是会话事件而非时间轮询（"节律"先住在记忆里，不住在触发器里）；
   纯时间触发留给到点预告 #20；
4. idle 传感器 v1 不参与（它属于收尾/离开节律族）。
