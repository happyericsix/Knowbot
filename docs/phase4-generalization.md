# Phase 4 入场券：泛化提案管道（L1 机械部分）

> 状态：小入场券（L1 规则），随机械实现同日落地。
> 依据：方案 §11 Phase 4（L1/L2 类级先验、提案管道、例外记忆）；A1 DDL
> 的 proposal 表（早已设计、零代码）；修订 §19 反驳修订版（agent 领地是
> 泛化与开放世界推断，不是基础归纳——本管道是确定性泛化，属查表领地）。
> **提前造机器，不提前做决定**：提案只进待确认区，用户裁决才生效。

## 1. L1 规则（实例 → 类）

**触发条件**（全部满足才生成提案）：
1. 某 class 作用域（audio.form_factor:X）下存在 ≥2 条 `audio.volume`
   **实例级**信念，state=active；
2. 全部 source=explicit（用户亲口确认过的才配泛化）；
3. 值一致：scalar 极差 ≤ 0.05；
4. 逐条置信 ≥ 0.7。

**提案内容**：
- 类信念 value ← 实例值（一致集合的最小值，取保守侧）；
- 置信 ← min(实例置信) × **迁移折扣 0.85**（封顶不高于来源，A1 原文）；
- source ← `inferred`（与 explicit/community 区分，推断可被纠正降级）。

**去重与抑制**：
- 同 (kind, 目标作用域) 已有 pending 提案 → 不重复生成；
- 曾被拒绝 → exception(pref_key, scope_key=类键, reason=proposal_rejected)
  → 永久抑制（A1 例外表一票否决复用）。

**运行方式**：daemon 内周期任务（默认 1h，纯 SQL 扫描，计算礼貌允许），
启动即跑一次。设备的类归属（form_factor）从 event_raw 事实流反查——
信念只存偏好，事实留在录像带里。

## 2. 明确不做（本轮）

- L2（类→全局）：需要 ≥2 个类分化后再做；
- 自动接受：提案永远进待确认区（哲学 3：显式与推断隔离）；
- 通知轰炸：提案不弹 toast，面板待确认区自见（管理审计走面板，
  交互总原则 §5）。

## 3. 验收

- 首条真实提案：当前库内 speakers 类有两条 explicit 实例（ZG2/Realtek，
  均 0.25 / conf≈0.93）→ 应生成"speakers 类先验升格"提案；
- 接受 → 类信念 source=inferred、置信 0.93×0.85≈0.79；新 speakers 设备
  首猜即用升格先验（方案 Phase 4 验收："新设备首猜显著优于裸类默认"）；
- 拒绝 → exception 落表，此后不再就同类提案打扰。
